# ロードマップ9 日別表の作成・取得 実装計画

## 1. 目的

管理者と作業者が、今日または未来日の作業に使う日別チェック表を`FULL_DAY`または`SPLIT`方式で作成し、過去日を含む作成済み表を取得できるようにする。

日別表は後続の数量・チェック更新が参照する業務履歴である。作成時点のカテゴリ名、道具名、在庫数、表示順をスナップショット保存し、マスター変更後も既存表の意味と上限を変えない。

対応Issueは [#25 ロードマップ9 日別表の作成・取得を実装する](https://github.com/Hiroyuki-12/FieldFlow/issues/25) とする。

## 2. Backend実装

### 2.1 API

| Method / Path | 権限 | 概要 |
| --- | --- | --- |
| `GET /api/v1/daily-checklists/:date` | 全ログインユーザー | 作成済みの日別表と全時間帯を取得する。未作成日は暗黙作成せず404を返す |
| `PUT /api/v1/daily-checklists/:date` | 全ログインユーザー | 作成方式と時間帯別カテゴリを指定し、冪等に作成または現在の表を返す |

Controllerは日付・Body・認証済みユーザーをServiceへ渡すHTTP入口とし、方式の整合性、日付制限、カテゴリ状態、Transaction、同時作成の収束はServiceへ集約する。

### 2.2 入力とレスポンス

- URLの日付は実在する`YYYY-MM-DD`だけを許可する。
- `FULL_DAY`は`FULL_DAY`時間帯を1件、`SPLIT`は`MORNING`と`AFTERNOON`を各1件必須とする。
- 各時間帯の`categoryIds`は重複のないUUID配列とし、有効な`WORK`カテゴリを1件以上指定する。
- `COMMON`カテゴリは利用者に明示指定させず、有効な共通道具だけをAPIが各時間帯へ自動追加する。
- レスポンスは時間帯、選択カテゴリ、道具項目を画面がそのまま表示できる公開型へ変換し、EntityのRelationや作成者の内部情報を公開しない。
- `editable`はAsia/Tokyoの今日以降なら`true`、過去日なら`false`とする。

### 2.3 Transaction、冪等性、同時作成

- ヘッダー、必要な全時間帯、時間帯別カテゴリ、対象道具項目を1つのTransactionで保存する。
- `SPLIT`の午前・午後を別Transactionにせず、片方だけ残る中途半端な表を防ぐ。
- 作成対象カテゴリと`COMMON`カテゴリをTransaction中にロックし、有効確認直後の利用停止やマスター変更を防ぐ。
- 同日・同方式の再送は、リクエスト側のカテゴリ差分を反映せず、現在の表をそのまま返す。
- 同日・異なる方式の再送は`409 CHECKLIST_ALREADY_CONFIGURED`で拒否する。
- 同時作成は`work_date`一意制約を最終防壁とし、一意制約に負けた処理をロールバックして、先に完成した同方式の表を返す。
- 過去日の`PUT`は`422 CHECKLIST_PAST_DATE`、未作成日の`GET`は`404 CHECKLIST_NOT_FOUND`とする。

### 2.4 スナップショット

- 選択した各`WORK`カテゴリについて、カテゴリ名と表示順を時間帯カテゴリへ保存する。
- 選択カテゴリおよび`COMMON`カテゴリに属する有効な道具だけを時間帯項目へ複製する。
- 道具名、カテゴリ名、在庫数、表示順を保存し、作成後のマスター編集・利用停止を既存表へ反映しない。
- 初期の持ち出し数は0、チェック状態は`false`、versionは1とする。

## 3. テスト計画

### Backend単体テスト

- 作成方式と時間帯構成の検証
- 過去日作成の拒否
- 未作成日取得の404
- 同方式再送の冪等性と異なる方式の409
- 選択カテゴリと共通道具のスナップショット作成
- Controllerが日付、DTO、現在ユーザーIDをServiceへ渡すこと

### Backend結合テスト

- ControllerからTypeORM、MySQLまでを通したGET／PUT API
- `FULL_DAY`の1時間帯と`SPLIT`の午前・午後2時間帯の一括作成
- 管理者・作業者の作成と取得、未認証401
- 過去日、方式不一致、無効・`COMMON`・存在しない・重複カテゴリの拒否
- 同方式再送で既存表・ID・項目が変わらないこと
- 同日への同時作成が一意制約により1件へ収束すること
- 作成後にマスターを変更してもレスポンスのスナップショットが変わらないこと
- Transaction途中の失敗でヘッダーや片方の時間帯だけが残らないこと

## 8. 実装結果

2026-08-17にIssue #25の計画作成、Backend実装、自動テスト、標準ポートでの起動確認を完了した。

### 8.1 Backend

- `DailyChecklistsModule`、Controller、Service、2 DTO、公開レスポンス型を追加し、CHECK-01の取得APIとCHECK-02の冪等作成APIを実装した。
- URLの日付を実在する`YYYY-MM-DD`へ限定し、作成方式と時間帯構成、時間帯ごとの重複しないカテゴリUUIDをDTOとServiceの二段階で検証した。
- Asia/Tokyoの業務日を基準に、過去日作成を`CHECKLIST_PAST_DATE`で拒否し、過去の作成済み表は`editable=false`で取得できるようにした。
- ヘッダー、`FULL_DAY`または午前・午後の全時間帯、選択カテゴリ、対象道具を1つのTransactionで保存した。
- 選択した有効な`WORK`カテゴリと自動追加する`COMMON`カテゴリをロックし、有効な道具だけを読取ロックしてからスナップショットを作成した。
- カテゴリ名・表示順、道具名・カテゴリ名・在庫数・表示順を履歴テーブルへ保存し、マスター編集や利用停止後も既存表のレスポンスが変わらないようにした。
- 同日・同方式の再送はカテゴリ差分を追加せず既存表を返し、異なる方式は`CHECKLIST_ALREADY_CONFIGURED`で拒否した。
- 同時作成では未作成日へのgap lockを避け、`work_date`一意制約に負けたTransactionをロールバックして先に完成した表を読み直すことで1件へ収束させた。

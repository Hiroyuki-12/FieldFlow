# 認証機能定義

## 目的

登録済みユーザーだけがFieldFlowを利用できるようにし、短命なAccess TokenとローテーションするRefresh Tokenで、安全性と操作継続性を両立する。

## 利用者と権限

- ログイン・Refreshは未認証でも呼び出せるが、認証情報が必要。
- ログアウト、自分の情報取得、パスワード変更はログイン済みユーザーが利用する。
- `mustChangePassword=true`のユーザーは、パスワード変更・Refresh・ログアウト以外の業務APIを利用できない。

## 正常フロー

1. ユーザーがログインIDとパスワードを入力する。
2. APIが利用状態とArgon2idハッシュを検証する。
3. Access Token（15分）をレスポンス本文、Refresh Token（7日）をHttpOnly Cookieで返す。
4. フロントはAccess Tokenをメモリだけに保持し、APIへ`Authorization: Bearer`で送る。
5. Access Token失効時はRefreshを1回だけ実行し、Refresh Tokenをローテーションして元のAPIを再試行する。
6. ログアウト時は現在端末のRefreshセッションを失効し、Cookieとメモリを消去する。

## 初期・再発行フロー

- 初期管理者は本番起動処理から分離した一回限りのSeedコマンドで作成する。
- ユーザー作成・仮パスワード再発行時は、暗号学的乱数による16文字の仮パスワードをAPIレスポンスへ一度だけ含める。
- 平文の仮パスワードはDB、アプリログ、監査ログに保存しない。
- 仮パスワードをそのまま新しいパスワードへ再設定する操作は拒否し、`mustChangePassword=true`を維持する。
- 初回パスワード変更が完了すると`mustChangePassword=false`になり、`authVersion`を更新してAccess TokenとRefreshセッションを全端末で失効し、再ログインを要求する。

## 入力制約

| 項目              | 制約                                                                 |
| ----------------- | -------------------------------------------------------------------- |
| loginId           | 4〜50文字、半角英数字と`._-`、大文字小文字を区別しない               |
| password          | 12〜128文字、空白を含むUnicode可、単純な文字種組合せルールは課さない |
| temporaryPassword | 16文字、自動生成のみ                                                 |

## 利用者向け画面と入力エラー

- Login画面は送信時にloginIdとpasswordを項目別に検証し、最初の不正項目へフォーカスする。Browser標準の検証文言ではFieldFlowの入力規則を一貫して説明できないため、Formは`novalidate`とし、Vue側でBackend DTOと同じ形式条件を確認する。
- Client側で判定できる形式違反は項目別に案内するが、APIが返す認証失敗は「ログインIDまたはパスワードが正しくありません」に統一する。登録済みloginIdの存在を画面から推測させないためである。
- 各項目のエラーは`aria-describedby`でinputと関連付け、該当項目だけを`aria-invalid=true`にする。エラー表示領域はあらかじめ高さを確保し、表示時に送信ボタンが大きく移動することを防ぐ。
- 利用者向け画面ではAccess TokenやRefresh Tokenの内部構造を説明せず、共用端末では利用後にログアウトするという実行可能な行動を案内する。開発者向けの本書とセキュリティ設計では正しい技術用語を維持する。
- パスワード変更画面は、Backendが`authVersion`とRefresh Sessionを全端末で失効する結果を「すべての端末からログアウトされる」「新しいパスワードで再ログインする」と説明する。初回変更と通常変更は同じ失効処理を通るため、同じ案内を表示する。

## 異常系

- ログイン失敗理由は「ログインIDまたはパスワードが正しくありません」に統一し、ユーザーの存在を漏らさない。
- 現在のパスワードと新しいパスワードが同じ場合は`PASSWORD_UNCHANGED`付きの`422`で拒否し、UserとRefresh Sessionを更新しない。
- 利用停止ユーザー、期限切れ・失効済み・再利用されたRefresh Tokenは`401`とする。
- 同一Refresh Tokenの再利用を検知した場合、そのユーザーのRefreshセッションをすべて失効する。
- ログインはアカウントと送信元を考慮してスロットリングし、5回失敗後は15分間制限する。

## 受け入れ条件

- Tokenやパスワードが永続的なブラウザストレージやログに残らない。
- 複数端末でログインでき、通常ログアウトは現在端末だけ、利用停止・パスワード変更は全端末へ反映される。
- Cookieの本番属性は`HttpOnly; Secure; SameSite=Lax; Path=/api/v1/auth`である。

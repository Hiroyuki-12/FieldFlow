# ロードマップ6 ユーザー管理 実装計画

## 1. 目的

管理者がチームの利用者、権限、利用状態を安全に管理できるようにする。
退職・異動後も日別表などの履歴を残すためユーザーは物理削除せず、利用停止で新規ログインと既存Sessionを無効化する。

対応Issueは [#17 ロードマップ6 ユーザー管理機能を実装する](https://github.com/Hiroyuki-12/FieldFlow/issues/17) とする。

## 2. Backend実装

### 2.1 API

| Method / Path | 概要 |
| --- | --- |
| `GET /api/v1/users` | 名前・ログインID検索、Role・状態絞り込み、ページング |
| `POST /api/v1/users` | ユーザー作成と仮パスワード発行 |
| `GET /api/v1/users/:id` | ユーザー詳細取得 |
| `PATCH /api/v1/users/:id` | 名前、ログインID、Role更新 |
| `PATCH /api/v1/users/:id/status` | 利用停止・再有効化 |
| `POST /api/v1/users/:id/temporary-password` | 仮パスワード再発行 |

全APIをJWT認証かつ`ADMIN`限定とする。ControllerはHTTP入出力を担当し、入力の正規化、競合判定、管理者保護、Session失効はServiceへ集約する。

### 2.2 入力とレスポンス

- 名前は前後空白を除去し、1〜100文字とする。
- ログインIDは前後空白を除去して小文字化し、4〜50文字の半角英数字・`.`・`_`・`-`だけを許可する。
- Roleは`ADMIN`または`WORKER`、状態は`ACTIVE`または`INACTIVE`だけを許可する。
- 更新・状態変更は現在画面が保持する`version`を必須とし、古い値は`409 USER_UPDATE_CONFLICT`で拒否する。
- 一覧・詳細レスポンスは`passwordHash`、`authVersion`、ログイン失敗情報を含めない。
- 作成・再発行レスポンスだけに平文の`temporaryPassword`を含める。

### 2.3 セキュリティと整合性

- 仮パスワードはNode.jsの暗号学的乱数で16文字生成し、Argon2idハッシュだけをDBへ保存する。
- 作成時と再発行時は`mustChangePassword=true`とし、初回変更画面を必須にする。
- 利用停止と仮パスワード再発行では`authVersion`を加算し、有効なRefresh Sessionを同じTransaction内で全件失効する。
- 自分自身の利用停止と`WORKER`への降格を拒否する。
- 最後の有効な管理者の利用停止と降格を拒否する。
- 有効な管理者一覧をTransaction内で悲観ロックし、2人の管理者を同時に相互降格させても管理者が0人にならないようにする。
- loginIdの一意制約違反はDBエラーをそのまま公開せず、`409 USER_LOGIN_ID_DUPLICATED`へ変換する。

## 3. Frontend実装

- 管理者専用Route`/users`と、PC・モバイルの管理ナビゲーションを追加する。
- 名前・ログインID検索、Role・状態フィルター、ページングを提供する。
- PCはテーブル、モバイルはカードでユーザーを表示する。
- 作成・編集・利用停止・再有効化・仮パスワード再発行を画面内ダイアログから操作する。
- 自分自身には停止と降格につながる操作を表示しない。ただし最終的な拒否はBackendで行う。
- 仮パスワードは作成・再発行直後のダイアログだけで表示し、ブラウザStorageへ保存しない。
- APIの業務エラーコードを、利用者が次の対応を判断できる日本語メッセージへ変換する。

## 9. 手動動作確認・理解チェック結果

2026-08-16に、ユーザー本人がブラウザを操作し、Codexが各処理におけるFrontend・Backend・DBの役割を説明する形式で動作確認を行った。資格情報、仮パスワード、Access Token、Refresh Tokenは本書へ記録していない。

### 9.1 手動で確認した操作

- 管理者としてログインすると「ユーザー管理」メニューと`/users`画面を利用できる。
- 条件を指定しない検索、名前・ログインIDの部分一致検索、権限・状態による絞り込み、および0件表示が正しく動く。
- 「ユーザー作成」を押した段階ではFrontend内でダイアログを表示するだけで、保存するまではBackendやDBを更新しない。
- ログインIDが3文字の場合、`minlength`によるブラウザ標準の入力チェックが働き、保存処理へ進まない。
- WORKERユーザーを新規作成すると仮パスワードが一度だけ表示され、初回ログイン後は初回パスワード変更画面へ遷移する。
- 初回パスワード変更後は通常のWORKERとしてログインできる。
- WORKERにはユーザー管理メニューが表示されず、URLを直接指定して`/users`を開いても`/forbidden`へ遷移する。
- 管理者によるユーザー名の編集がDBへ反映され、一覧の再検索後にも変更後の名前が表示される。
- ユーザーを利用停止すると、そのユーザーによる再ログインは汎用的な認証エラーで拒否される。
- 利用停止したユーザーを再有効化すると、再びログインできる。
- 仮パスワードを再発行し、新しい仮パスワードで初回パスワード変更へ進める。
- 既存のログインIDを指定したユーザー作成は「同じログインIDのユーザーはすでに存在します」と表示される。
- ログイン中の管理者自身については、権限変更の選択欄が無効になり、利用停止ボタンも表示されない。
- 同じユーザーを2つの画面で開き、片方を先に保存すると、古い`version`を持つもう片方の保存は「他の管理者が先に更新しました。一覧を再読み込みしてください」と拒否される。先に保存した名前は上書きされずに残る。
- 360px幅でもユーザー管理画面全体に横スクロールが発生せず、主要操作を利用できる。

### 9.2 今回整理した設計上の役割

- 検索条件は単純で、検索対象を表す情報のため、GETリクエストのクエリパラメータとして送る。作成・更新内容はPOST・PATCHリクエストのJSON本文として送る。
- JSONにすれば暗号化されるわけではない。URLに置かないパスワードなどの情報も含め、通信経路の保護はHTTPSが担当する。
- Frontendの入力チェックやルーターガードは、誤操作を減らして分かりやすい画面遷移を作るための仕組みである。APIへの直接アクセスは可能なので、認証・認可の最終的な防御はBackendが担当する。
- Backendは入力値と権限を検証し、業務ルールを適用してからDBを操作する。DBは検索・追加・更新を行い、ログインIDの一意制約などでデータ整合性の最後の防壁になる。
- ユーザーは物理削除せず、`INACTIVE`へ変更して過去の記録との関係を維持する。
- 仮パスワードはBackendで生成し、DBにはArgon2idのハッシュだけを保存する。仮パスワード中は`mustChangePassword = true`で、本人が新しいパスワードへ変更すると`false`になる。
- `version`はユーザー行の更新競合を検知するための値である。古い`version`による更新は、DBを書き換える前に拒否して「後勝ちの上書き」を防ぐ。失敗後に変更を戻すロールバック機能そのものではない。
- `authVersion`は認証状態を世代管理する値であり、利用停止や仮パスワード再発行など、既存の認証を無効にする操作で更新する。Refresh Sessionはログイン端末ごとに保持される更新用セッションであり、`version`とは役割が異なる。
- 現時点では管理者を同格として扱う。別の管理者の降格・利用停止は許可する一方、本人自身の降格・利用停止、および有効な最後の管理者を失う操作は禁止する。

### 9.3 自動テストで補完している確認

次の項目は画面上の挙動だけでは内部状態まで断定できないため、自動テストで確認している。

- WORKERのAccess Tokenを使ってユーザー管理APIへ直接アクセスしても、BackendがHTTP 403で拒否する。
- 利用停止・仮パスワード再発行時に、対象ユーザーの全Refresh Sessionを同一Transaction内で失効する。
- 認証状態が変わった後は、古いAccess Tokenを`authVersion`で拒否する。
- 2人の管理者が同時に相互降格を試みても、悲観ロックによって少なくとも1人の有効な管理者が残る。
- 1ページの上限を超えた場合に「次へ」で2ページ目を取得し、最終ページではボタンが無効になる。

### 9.4 理解度の記録

理解度は約80%と判断した。

良かった点:

- Frontend・Backend・DBの大まかな責務と、Frontendだけではセキュリティを守れない理由を説明できた。
- 仮パスワード、`mustChangePassword`、権限別の画面表示、利用停止、楽観ロックの動作を実際の操作と結び付けて確認できた。
- 管理者の階層を増やす案と、同格の管理者を維持する案の運用上の違いを検討し、現時点の方針を決められた。

今後補強する点:

- DBは通常のユーザー管理で物理削除を行わず、状態を更新して履歴を残すこと。
- `version`は競合した更新を事前に拒否する値であり、更新済みデータを後から元へ戻す値ではないこと。
- `version`、`authVersion`、Refresh Sessionの役割と、各値を更新・失効させる条件を区別すること。

## 10. 改善実施結果と引き継ぎ

ロードマップ6の続きを扱う場合は、本節と「9. 手動動作確認・理解チェック結果」を確認する。

### 10.1 認証処理と管理用`version`の分離

`users.version`は、管理者が画面から変更する項目の競合検知専用とした。TypeORMの`@VersionColumn`による全保存時の自動加算を使わず、通常の`@Column`をUsersServiceから明示的に加算する。

- 名前・ログインID・Roleの編集、利用停止・再有効化、仮パスワード再発行では`version`を1加算する。
- ログイン成功・失敗、ロック状態の更新、本人のパスワード変更では`version`を加算しない。
- 認証用の`authVersion`、ログイン失敗回数、ロック期限は従来どおり各責務に応じて更新する。
- DB列の型・名前・既定値は変わらないため、新しいMigrationは不要と判断した。

認証処理後に管理用`version`が変わらないことと、管理操作では1ずつ進むことをTestcontainers MySQLで確認する。

### 10.2 利用停止ダイアログの文言

利用停止ダイアログからAccess Token・Refresh Sessionという内部用語を外し、利用者が影響を判断できる次の説明へ変更した。

> 「○○さんを利用停止しますか？ 利用停止すると、すべての端末で操作できなくなり、再有効化するまでログインできません。過去の記録は削除されません。」

仮パスワード再発行も「現在のパスワードではログインできなくなり、すべての端末からログアウトされる」と説明する。技術的な失効処理は設計書やコードコメントへ残す。

### 10.3 重複したBackend結合テストファイル

`backend/test/health.integration-spec 2.ts`は、正規の`backend/test/health.integration-spec.ts`より古く、`Server`型指定と整形だけが不足した未追跡コピーであることを比較確認した。

ユーザー承認後に古いコピーだけを削除した。正規の結合テストは残しており、Backend全体lintを除外なしで実行する。

# 日付別チェック機能定義

## 目的

特定日の作業に必要な道具、持ち出す数、準備状態をチームで共有し、道具忘れと確認漏れを減らす。

## チェック表の構成

- 1チーム・1日につき現行の`ACTIVE`ヘッダーを1件だけ持つ。変更前・削除前のヘッダーは`CANCELLED`として複数保持できる。
- ヘッダーは`FULL_DAY`または`SPLIT`の作成方式を持つ。今日・未来日は、旧版を上書きせず取消履歴へ移して新版を作ることで方式を変更できる。
- `FULL_DAY`は`FULL_DAY`時間帯を1件、`SPLIT`は`MORNING`と`AFTERNOON`時間帯を各1件持つ。同じ日に両方式を混在させない。
- 各時間帯は選択した作業カテゴリを1件以上保持する。`SPLIT`では午前と午後のカテゴリを同じ作成操作で別々に選び、一括保存する。
- 各時間帯には、選択した作業カテゴリに属する有効な道具と`共通`カテゴリの有効な道具を複製する。
- 道具名、作業カテゴリ名、在庫数、表示順はスナップショット保存し、マスター変更を既存表へ自動反映しない。

## 正常系: 表の生成

- ログイン後はホームを表示し、今日の作成・既存チェック・別日の確認の起点とする。
- 今日・未来日は、作成方式と時間帯ごとの`categoryIds`を指定して`PUT`で冪等に作成する。
- 同じ日への同時作成は`workDate`の一意制約とトランザクションで1件へ収束させる。既存表と同じ作成方式の再送は、後からカテゴリが追加されていても現在の表を返す。異なる作成方式の再送は`409 CHECKLIST_ALREADY_CONFIGURED`とする。
- 過去日に表がなければ`GET`は`404 CHECKLIST_NOT_FOUND`を返し、暗黙作成しない。

## 表の操作

- 管理者と作業者は日付・時間帯の選択、閲覧、今日・未来日の持ち出し数・チェック状態更新を行える。
- 今日・未来日は`時間帯・作業内容を変更する`から現在の設定を修正できる。同じ時間帯・同じ道具は数量と準備状態を引き継ぎ、それ以外は新しいスナップショットとして作り直す。
- 今日・未来日は、通常の追加・変更操作から分離した`その他の操作`内の`この日のチェック表を削除する`から現行版を取り消せる。取消後の通常取得は404となり、同じ日に新しい表を作成できる。
- 変更・削除前の版と入力値は物理削除せず保持する。入力済み内容がある場合は影響を説明し、利用者が確認した場合だけ実行する。
- `SPLIT`では午前・午後の切り替え時も、それぞれのカテゴリ、数量、チェック状態を独立して保持する。
- 更新は行単位で自動保存し、成功時に更新後の`version`を返す。
- 管理者と作業者は作成済みの今日・未来日の時間帯へ、未選択の有効な作業カテゴリを追加できる。
- カテゴリ追加時は、そのカテゴリの有効な道具を同じトランザクションで複製する。同じカテゴリ・同じ道具は同じ時間帯へ1回だけ追加できる。

## 画面表示ルール

- 道具行は、道具名・在庫・持ち出し数・準備状態をスマートフォンの幅に応じて折り返し、長い名称でも数量操作や状態表示と重ねず、横スクロールを発生させない。
- 通常の保存状態は画面全体に1件だけ表示する。道具行には処理中の`保存中…`、`保存失敗`と再試行、競合内容など、その道具で確認・対応が必要な状態だけを表示する。
- 画面全体の保存状態は`競合`、`保存失敗`、`保存中または保存待ち`、`すべて保存済み`の順に優先する。全項目にpending・running・失敗・未解決競合がない場合だけ`すべて保存済み`とする。
- 数量を1以上にした道具だけを「持ち出し対象の準備数」の分母とする。カテゴリ内に数量1以上の道具が1件もない場合は、カテゴリ見出しを`持ち出し未設定`とする。
- 上部の進捗は、持ち出し対象の`準備済み数 / 対象数`と`数量未設定カテゴリ数`を別々に表示する。数量未設定が0カテゴリ、持ち出し対象が1件以上、かつ対象が全て準備済みの場合だけ`準備完了`と表示する。
- `共通`はスナップショット道具が1件以上存在する場合に同じ未設定判定を行う。共通道具が0件の場合は、存在しない確認対象を仮想的に未設定として数えない。
- MVPの数量0は「意図的に持ち出さない」と「未確認」を区別できない。忘れ物を防ぐため表示上は確認が必要な状態とし、確認済みで持ち出さない状態の永続化は将来の別要件とする。
- 削除操作は折りたたまれた`その他の操作`へ配置し、通常の追加・変更ボタンと同じ操作群に並べない。確認ダイアログでは対象日、削除される入力、新規作成できること、内部履歴を保持することを説明し、初期フォーカスは`キャンセル`とする。
- スマートフォンでは日付・カテゴリ変更を折りたたみ、時間帯・進捗・選択中カテゴリを常時表示する。
- 作成ダイアログは内容部分だけをスクロールさせ、見出しと操作ボタンを表示領域に残す。
- 作成・設定変更ダイアログは、`FULL_DAY`で1カテゴリ以上、`SPLIT`で午前・午後の両方に1カテゴリ以上が選択されるまで保存ボタンを無効にする。読み込み中と選択候補0件も無効とし、理由をボタン付近に文章で表示する。submit側の検証も残し、検証エラー時は最初に不足する時間帯の選択欄へフォーカスとスクロールを移す。
- 日別チェックへ遷移したときは画面先頭から表示する。

### 表示用語

| 用語                   | 定義                                                                                                             |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 持ち出し対象外         | 道具の持ち出し数が0で、現在は準備確認の対象ではない状態。準備済みチェックは無効にする                            |
| 未準備                 | 持ち出し数が1以上で、まだ準備済みとして確認されていない道具の状態                                                |
| 準備済み               | 持ち出し数が1以上で、準備完了を利用者が確認した道具の状態                                                        |
| 持ち出し未設定カテゴリ | カテゴリ内に持ち出し数1以上の道具が1件もない状態。上部の数量未設定カテゴリ数と同じ集計結果を使う                 |
| 自動保存               | 数量または準備状態の変更を、保存ボタンなしで道具ごとの独立したキューから順番に保存する仕組み                     |
| 保存失敗               | 通信や入力エラーにより、画面上の変更を保存済みとして扱えない状態。該当行から再試行できる                         |
| 競合                   | 他の利用者が先に同じデータを更新し、送信したversionがDBの現行versionと一致しない状態。最新値へ戻して確認を求める |

数量0は画面上で`持ち出し対象外`と表示するが、MVPのデータ構造には「持ち出さないことを確認済み」を保存する項目がない。そのため、意図的な対象外と未確認は区別できず、カテゴリ内の全道具が数量0なら`持ち出し未設定カテゴリ`として扱う。

## 入力・状態ルール

| 項目 | ルール |
| --- | --- |
| scheduleMode | `FULL_DAY`または`SPLIT`。今日・未来日は版を作り直して変更可 |
| period | `FULL_DAY`、`MORNING`、`AFTERNOON`。scheduleModeと整合すること |
| categoryIds | 各時間帯で有効な`WORK`カテゴリを1件以上指定 |
| takeoutQuantity | 0〜`stockQuantitySnapshot`の整数 |
| checked | 数量1以上のときだけ`true`可 |
| 数量を0へ変更 | 同一トランザクションで`checked=false` |
| 過去日 | 閲覧のみ、作成・カテゴリ追加・更新不可 |
| version | リクエスト値とDB値が一致するときだけ更新 |
| 設定変更の引継ぎ | 同じ時間帯・同じ道具だけ数量と準備状態を引き継ぐ。在庫上限を超える旧数量は0・未準備へ戻す |
| 表の削除 | 現行版を`CANCELLED`にし、`cancelledByUserId`と`cancelledAt`を保存。物理削除しない |

## 競合時の扱い

- バージョン不一致は`409 CHECKLIST_ITEM_UPDATE_CONFLICT`とし、`details.currentItem`に最新行を含める。
- 設定変更・削除ではヘッダーの`id`と`version`を比較し、不一致は`409 CHECKLIST_UPDATE_CONFLICT`とする。
- フロントは編集中の値を破棄して最新行を表示し、「他のユーザーが更新しました」と通知する。
- MVPでは自動マージやリアルタイムPush配信を行わない。別ユーザーの更新は再取得・再訪時に反映する。

## 異常系

- 過去日の作成・カテゴリ追加・更新、方式と時間帯の不整合、在庫超過、数量0でのチェックは`422`とする。
- 存在しない日別表・時間帯・項目・道具は`404`とする。
- 無効カテゴリ、`COMMON`カテゴリの明示指定、カテゴリ・道具の重複追加は`409`または`422`とする。
- 通信失敗時は画面上の値を「保存済み」と扱わず、再試行できる状態を表示する。

## 受け入れ条件

- 1日通しでは1つ、午前・午後では異なるカテゴリを持つ2つの時間帯が一括作成される。
- 午前・午後を切り替えても、各時間帯のカテゴリ、数量、チェック状態が混ざらない。
- マスター変更後も作成済みの表の名称・カテゴリ・上限数が変わらない。
- 在庫超過、数量0でのチェック、過去日更新、カテゴリ・道具の重複追加がAPIで拒否される。
- 管理者と作業者のどちらも、今日・未来日の時間帯へ未選択の作業カテゴリを追加できる。
- 今日・未来日の設定を変更でき、同じ時間帯・同じ道具の入力値が引き継がれる。
- 入力済み内容がある設定変更・削除は確認なしで実行されず、削除後は同日に再作成できる。
- 変更前・削除前の表、入力値、実行者、実行時刻が内部履歴として残る。
- 数量未設定カテゴリが残る場合は、持ち出し対象が全て準備済みでも「確認が必要」と表示される。
- 作成・設定変更は、方式ごとに必要なカテゴリが揃うまで実行できず、不足する入力箇所を画面と支援技術の両方から理解できる。
